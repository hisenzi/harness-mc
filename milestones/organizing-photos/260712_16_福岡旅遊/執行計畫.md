## 執行階段

### 階段一：建立統一 project、work anchor 與工作包

1. 在既有空目錄 `milestones/organizing-photos/` 建立 internal `project.json`；記錄單一專案邊界、工作包命名規則、無固定 due 與原照片不進 Git。
2. 建立 `tasks.json`，以 `fukuoka-travel-photo-organize-v1` 作為本次 work anchor，包含目標、狀態、done condition 與本驗收矩陣。
3. 建立 `260712_16_福岡旅遊/` 工作包並放入本執行計畫；此三步只建立專案文件，不碰原照片。
4. 通過 Repo Ready、target-specific topology admission、task validator 與 MC data build，確認 unified project 可被讀取。
5. 進入照片整理 execution 後，才建立 `來源檔案manifest.csv`：原檔名、格式、位元組、影像尺寸、可讀取的拍攝日期／時間及 SHA-256。
6. 驗證 manifest 恰有 582 個唯一來源；發現來源數或內容已變動即停止。

輸出物：`project.json`、`tasks.json`、`260712_16_福岡旅遊/執行計畫.md`、`來源檔案manifest.csv`。

### 階段二：全量視覺審閱與分類標記

1. 產生只供審閱的分批縮圖索引，不修改來源影像。
2. 逐批審閱全部 582 個來源；對精選候選、淘汰候選及場景不明者開啟較大尺寸複核。
3. 每個來源標記：日期、行程／場景、保留／淘汰、FB 入選狀態、攝影作品分數及理由。
4. 無法可靠判斷日期或場景者進 `90_待辨識`，不猜測。

淘汰候選包含：較弱重複照、意外失焦、不可挽救的曝光、無敘事價值的截圖或明顯誤拍。刻意模糊、特殊曝光或具有敘事作用者不因技術表象自動淘汰。

輸出物：`照片審閱結果.csv`。

### 階段三：產生 dry-run 新舊路徑對照

1. 依拍攝順序產生唯一新檔名：`YYMMDD_Dn_場景_流水號_IMG原編號.ext`。
2. 產生每個來源的舊路徑、新路徑與原因；不立即移動。
3. 檢查 582 個來源皆只有一個歸檔目的地、新檔名無碰撞、目的地不覆寫既有檔案。
4. FB 精選依故事順序編為 `FB_001` 起；攝影作品保留原歸檔名稱並在 manifest 記錄分數。

輸出物：`新舊檔名對照_dry-run.csv`、dry-run verifier 結果。

### 階段四：一次套用分類、改名與精選複製

1. 依已驗證 dry-run 對照移動並改名 582 個來源。
2. 淘汰候選只移入 `_審核後刪除`，不呼叫永久刪除命令。
3. 從保留來源複製 40–60 張至 `80_FB精選`；重視五日旅程敘事、人物、食物、景點、細節、移動與收尾，每個近似場景通常只取最強一張。
4. 攝影作品先評分：構圖 25、光線色彩 20、瞬間故事 20、個人觀點 20、技術品質 15；候選門檻 75，正式入選門檻 82，最終複製 12–18 張至 `81_攝影作品精選`。
5. 同一來源可以同時進入 FB 與攝影作品精選。

輸出物：五日行程資料夾、`80_FB精選`、`81_攝影作品精選`、`90_待辨識`、`_審核後刪除`。

### 階段五：完整性驗證與結案

1. 重新盤點來源歸檔：五日行程＋`90_待辨識`＋`_審核後刪除` 合計必須恰為 582。
2. 以 SHA-256 驗證移動／改名後內容與來源 manifest 完全一致。
3. 驗證沒有舊檔殘留、沒有未列入對照的來源、沒有目的地檔名碰撞或零位元檔案。
4. 驗證 FB 與攝影作品精選均可追溯至一個來源歸檔檔案。
5. 產生 `整理完成報告.md`，列出各資料夾數量、FB／作品入選數、淘汰數、待辨識數、例外與未完成事項；將 task 更新為 completed。

輸出物：`新舊檔名對照.csv`、`整理完成報告.md`、completed task anchor。

## 風險與停止條件

- 執行期間來源檔案數、名稱、大小或內容雜湊改變：停止，避免與其他 session 重疊。
- EXIF／拍攝日期缺失或時區不可靠：使用檔名相鄰順序與畫面輔助；仍不可靠就放 `90_待辨識`。
- 新檔名碰撞、目的地已有未列入 manifest 的同名檔案、來源無法讀取：停止，不覆寫。
- 任何命令可能永久刪除來源：禁止執行。
- FB／作品精選是複本；若磁碟空間不足，停止並回報，不以 symlink 或降畫質替代。
